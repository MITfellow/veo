## Built

### The model port (L1) — `src/substrate/model/types.ts`

A provider is an **external, untrusted surface**, so every chunk is
zod-validated at the boundary and the error names the provider.

```
{type:'text-delta', text}   {type:'tool-call', id, name, input}
{type:'usage', inputTokens, outputTokens, costMicros}
{type:'finish', reason}     {type:'error', kind, message, retryable}
```

Three choices worth their lines:

- **Streaming is the only mode.** No `complete()`. A non-streaming provider is
  a one-chunk stream; the reverse costs first-token latency forever, and §32
  budgets first token at <1.5s.
- **Failure is a chunk, not an exception** (invariant 13). A stream that
  emitted 400 good tokens and then died says so without discarding them.
- **Usage accumulates, never overwrites.** Providers differ on whether they
  report usage once or incrementally; overwriting silently halves the bill for
  the incremental ones.

### The run loop (L5) — `src/orchestration/runner.ts`

```
run.started → [ step.started → assemble → model.requested → stream
                → model.responded|failed → step.finished ]* → run.finished
```

**`step.started` is appended before the model is called**, `step.finished`
after. A `step.started` with no matching `step.finished` *is* the definition of
an interrupted step — no status column that the dying process would have had to
write. The `steps` projection makes that a one-row index lookup
(`finished_at IS NULL`).

**All six stop conditions, each named** in `run.finished.reason` (decision
015): `stop`, `step-cap`, `token-cap`, `time-cap`, `cost-cap`,
`tools-unavailable`, `loop-detected`. Caps are checked **before** a step, never
mid-stream — aborting a call halfway to save 200 tokens wastes the 2,000
already spent and leaves a partial answer nobody can use.

**Cancellation** keeps the partial text. The user watched those words appear;
making them vanish is worse than stopping.

**Loop detection** keys on `tool + canonicalJson(input)`, so `{a:1,b:2}` and
`{b:2,a:1}` count as the same call — which is exactly the loop models actually
get stuck in. Three → corrective observation, four → abort.

**Tool calls are parsed and recorded** as `tool.requested`, then the run stops
with `tools-unavailable`. The shape of the tool path is exercised end to end;
only execution is missing, so M3 is additive rather than a rewrite.

### Context assembly (L4) — `src/cognition/context/assemble.ts`

M2 ships three of §21's fourteen blocks, but ships the whole *contract*: pure,
deterministic, budgeted, and **it reports what it evicted**. Silent truncation
is how an assembler lies to you — the model gets less than you think and
nothing says so. A golden file (`test/golden/context.golden.txt`) makes every
future change to it visible in review.

FOREIGN content is fenced with explicit untrusted-data delimiters. This is
**defence in depth and nothing more**: the real defence is the trust lattice
from M1, and M4 runs the injection corpus with the fence removed to prove the
refusal does not depend on a string the model is free to ignore.

### Interface (L6) — `src/interface/`

`node:http`, no framework (decision 016). `POST /sessions`, `GET /sessions`,
`GET /sessions/:id`, `POST /sessions/:id/messages` → `202 {runId}`,
`GET /runs/:id/stream`, `POST /runs/:id/cancel`, `GET /runs/:id/trace`,
`GET /health`.

**The SSE id is the event-log sequence number** (decision 017). Resume is a log
read, so it shares one code path with live streaming, survives a server
restart, needs no ring buffer, and works for a run that finished months ago.
That is only cheap because M0 made `seq` dense and transactional.

## The three bugs the tests found

Fixed in the source. No test was weakened.

1. **The caps were unreachable.** A stream that ended *without* a `finish`
   chunk was treated as a completed answer, so the loop always returned after
   one step and none of §26's four caps could ever fire. A stream that ended
   without the provider saying it was done did not complete — the socket
   dropped, the provider stalled. The loop now goes round again and a cap
   catches it. Four of the six stop-condition tests failed on this.
2. **Cancellation lost the partial text.** The stream totals were created
   inside `stream()`, so an abort threw them away along with everything the
   user had already watched appear. The caller owns the totals now.
3. **The truncation note caused the truncation it described.** The note was
   appended to the Situation block *after* budgeting, pushing the context over
   its ceiling. Its cost is reserved up front.

A fourth was caught by the database rather than a test: `createTestSubstrate`
ignored any db path and always used `:memory:`, so a "process restart" test
silently got an empty database and would have passed while proving nothing.
With a real file, the seeded fake ids regenerated process 1's ULIDs and hit the
`UNIQUE` constraint on `events.id` — the substrate defending itself correctly
against an unrealistic fixture.

Also deferred, deliberately:

- **A real provider adapter.** The design note planned an `OpenAIAdapter` this
  milestone. It is not written. The port, the fake and the loop are all
  provider-shaped and tested; the adapter is a day's work with no architectural
  content, and writing it *before* M3 fixes the tool-call wire format would
  mean writing it twice. Called out here rather than quietly dropped.
- **Degradation ladder (§27).** `GET /health` reports a level and the Situation
  block carries it, but nothing *transitions* yet — the triggers are an
  embedder (M6), a fallback provider (M3), and disk/vault states. Writing the
  ladder before the things that trigger it would be fiction.

## Unsure

- **Suspension is modelled but not exercised.** `run.suspended`/`run.resumed`
  exist in the schema and the runner releases all resources on return, but
  nothing suspends yet because nothing can ask for approval until M4. The
  "survives a full restart" test covers a *new process continuing a
  conversation*, which is the substrate half of the guarantee; the parked-run
  half is M4's to prove. I would rather say that than imply it is done.
- **Two concurrent runs in one session are allowed.** The adversarial test
  shows they do not corrupt each other, but it is not obvious they should be
  permitted at all — two agents answering the same person at once is confusing
  for the person. M4's policy layer is where that call belongs.
- **The `delta` SSE frame has no durable id** (it is sent with `id: -1`) because
  deltas are not events — appending one event per token would multiply the log
  by a thousand for no recoverable information. The consequence: a client that
  reconnects mid-stream gets the completed `message` frame rather than the
  remaining deltas. That is the right trade, but it means resume is
  message-granular, not token-granular, and the §29 line "must never lose
  output" is satisfied in substance rather than literally.
- **`historyFor` reads the whole session on every step.** Fine at 200 turns,
  O(session) forever. M5's assembler needs a windowed read anyway.
