# M8 — Time & proactivity

**Status:** done · 793 agent tests green (63 new) · 140 web · `tsc` clean ·
`npm run demo:m8`

**Done-when (§33):** *"every weekday 9am" survives restarts, a timezone
change and a 3-day outage, with correct catch-up.* That is test 48 in
`test/integration/scheduler.test.ts`, executed end to end on a fake clock.

This is the milestone where the agent stops being a thing you talk to and
starts being a thing that can talk to you. §28's own note is that it needs
"zero kernel changes" — a scheduled run is an ordinary run whose trigger
happens to be `schedule` — and that turned out to be true: the composition
root gained a handler, the runner gained one optional field, and nothing
in the run loop moved.

The organising position is in `docs/decisions/033`: **the lease is not an
event.** Everything else follows from taking that seriously — what gets
written to the log, what a crash can strand, and what a rebuild is allowed
to resurrect.

## Built

**Cron, on a wall clock (§28).** `src/orchestration/cron.ts`.

- A 5-field parser: steps, ranges, lists, names (`mon`, `jan`), and the
  `@daily`/`@hourly` aliases. `validateCron()` is the same code path the
  HTTP route uses, so a typo is a 400 that explains itself rather than a
  schedule that never fires.
- `nextFireAfter` walks **local wall-clock minutes** via `Intl`, not UTC
  instants with an offset added. This is the whole DST story: 9am stays
  9am because the search space is wall time and the instant is derived
  from it, never the reverse.
- `instantOfLocal` does two refinement passes and returns `null` in the
  spring-forward gap. A schedule for 02:30 simply does not fire on the day
  02:30 does not exist — which is both correct and the only honest answer.
  Fall-back 01:30 fires once, because `due()` always asks strictly after
  `lastFiredAt`.
- `MIN_INTERVAL_MS = 5min`. `* * * * *` is refused with the word "denial
  of service" in the message: a per-minute schedule on an agent that calls
  a paid model is an attack whether or not anyone meant it as one.

**A durable queue (§28).** `src/orchestration/queue.ts`, schema `011`.

- `enqueue / lease / complete / fail / get / list / deadLetters / replay /
  cancelPendingForSchedule / counts`.
- Leases are fenced by token; `lease_until IS NULL` counts as expired so a
  crash between `job.started` and the lease write cannot strand a job.
- Backoff is `FNV-1a(jobId:attempt)` scaled into `[0.5, 1.5)`, not
  `Math.random`. §8 says replaying the log reproduces the state; a random
  jitter would make that false for every retry delay in the system.
  `MAX_BACKOFF_MS = 15min`.
- Idempotency is a partial unique index over `status IN ('pending',
  'leased')` only — so the same slot cannot be queued twice *now*, while
  next week's identical key is still free.
- A dead letter keeps the dead row and `replay()` creates a **new** job.
  The failed attempt is part of the record of what this agent did.

**Schedules (§28).** `src/orchestration/schedule.ts`.

- `create / update / delete / get / list / due / specOf`, cron and
  one-shot, with the catch-up policy per schedule.
- `due()` is the only thing that fires anything, and it is pure with
  respect to the clock: the tests move time rather than waiting.
- Catch-up defaults to **`fire-once`** (`docs/decisions/034`), capped at
  `MAX_CATCH_UP = 10` for `fire-all`, and every skipped slot emits
  `schedule.missed` under all three policies — so the number of mornings
  that happened without you is honest regardless of what ran.

**A worker that yields (§28).** `src/orchestration/worker.ts`.

- `tick()` is one unit of work and is what the tests drive; `start()` is
  `setInterval` + `unref`; `stop()` sets `stopping` *before* awaiting, so
  shutdown refuses new work and then finishes what is in hand.
- `busy()` is how "interactive runs always have strict priority" is
  implemented: the worker does not lease while a user run is in flight.
  The HTTP layer increments a counter on run start and decrements on end.
  A yielded tick does **not** burn an attempt — being polite is not a
  failure.

**The degradation ladder (§27).** `src/orchestration/degradation.ts`.

- `report / clear / current / state / guard`, levels L0–L4 with a
  user-facing sentence each.
- The level is the **max of the active signals**, not the most recent one:
  `embedder→L1, model→L2, storage→L3, vault→L4`. Only transitions emit
  `degradation.changed`, so a provider flapping does not flood the log.
- Wired at the composition root, including at boot: with no
  `ARISH_API_KEY` the agent reports L2 against itself and says why. The
  `/health` endpoint now answers `L2` in that configuration rather than
  `L0`, and `test/integration/app.test.ts` asserts it.

**The surface.** `GET/POST /schedules`, `PATCH/DELETE /schedules/:id`,
`GET /jobs`, `GET /jobs/dead-letter`, `POST /jobs/:id/replay`,
`GET /degradation`, and `GET /events` (listed in §29, unbuilt until a
milestone needed it). In Veo, **Settings → Standing instructions**:
next fire in local wall time with the zone named, missed counts shown,
catch-up as a visible control, dead letters listed with their last error,
and the ladder as a banner when it is not L0.

**The context knows why it woke up.** `Situation` gained an optional
`triggerDetail`, so a scheduled run renders *"This run was triggered by:
schedule (your schedule "Morning briefing"). Nobody is necessarily
waiting: say why you are speaking, and be brief."* Template versions
bumped to `situation-2` / `tpl-3`; new golden scenario `scheduled-run`
(16 total).

## Found

**DERIVED could schedule.** Test 57 failed on its first run: `M1` gave
`schedule:create` to DERIVED, i.e. to model output, i.e. downstream of
every fenced page the agent has ever read. A caught injection today
becomes a job that fires tomorrow, when the fence is long gone. Removed
from the ceiling — `docs/decisions/035`, written rather than quietly
patched because it changes an earlier milestone's lattice.

**A payload could rename itself.** `ScheduleStore` spread the user's
payload *after* the fields it controls, so `{ scheduleId: 'spoofed' }`
won. Fixed by spreading the payload first; test 60 holds the line.

**Two of the first three timezone tests were wrong, not the code.**
Moving a 9am schedule from New York to Lisbon at 08:00 NY does **not**
fire in Lisbon that morning — it is already 13:00 there. The expectation
was corrected (with the reasoning in the test), not the behaviour:
re-anchoring from *now* is what makes "9am" keep meaning 9am, and flying
east costing you today's alarm is what a physical alarm clock does too.

## Deferred

- **One worker.** The lease machinery is built for several and the fencing
  is real, but nothing starts a second one. Multi-worker is a question for
  a deployment this system does not have.
- **`effectsCommitted` is still `[]`.** The outbox read model M7 owed is
  still owed; M9.
- **No natural-language scheduling.** "every weekday at 9" is a preset in
  the UI and a cron string underneath. Parsing English dates is a model
  task, and doing it badly would produce schedules that fire at the wrong
  time while looking friendly.
- **No notification when a background run finishes.** The run is in the
  session and the UI shows it on next load; it does not push. §28 does not
  ask for it and the browser surface for it is a separate decision.

---

## Unsure

- **Whether `fire-once` is right for effectful schedules.** For a briefing
  it plainly is. For "pay the invoice on the 1st", running only the most
  recent missed slot is a judgement call the user cannot currently make
  per-schedule beyond the three policies. There is no effectful scheduled
  tool today, so the question is not yet live.
- **The five-minute floor.** It is the right default and it is also the
  kind of limit a legitimate user eventually hits. It is a constant, not a
  config key, until someone has an actual reason.
- **`MAX_CATCH_UP = 10`.** The cap is reported, so it is visible rather
  than silent, but the number is a guess.
- **Whether the worker should drain the queue on shutdown.** Today it
  finishes the job in hand and leaves the rest pending, which is correct
  for a laptop and possibly wrong for a container that is being replaced.
