# M6 — Memory

**Status:** done · 636 tests green (57 new) · `tsc` clean · `npm run demo:m6`

§33 calls this "the milestone that matters most", and the bar it sets is not
"facts go in and come out" — it is *a fresh session visibly knows the person
from turn one*, and the agent is **wrong about them less often over time
rather than more**. Test 36 asserts the first clause against the assembled
context. The second clause is not a test, it is a set of design choices that
all point the same way, and most of them are refusals.

---

## Built

**The stores (§22.1–22.4).** `src/cognition/memory/`, eight tables behind
migration 007.

- **Semantic** — facts, bitemporal, inherited from M1's projector. Valid time
  and transaction time are separate and stay separate: `memory.superseded`
  closes valid time (the world changed, "where did she work in March?" still
  answers), `memory.corrected` closes transaction time (we were wrong).
- **Episodic** — one row per run: request, response, actions, outcome.
- **Procedural** — rules with `applied` / `overridden` counters, probation at
  3, retirement at 5, both as events.
- **Affective** — four dials, never updated from a single episode, never
  from demographics, 12-episode floor before it moves at all.

**The write path (§22.5).** `extract → gate → resolve → reconcile → emit`,
hung off the *end* of a run (`RunObserver`), never on the user's critical
path. Test 37 asserts the latency.

**The gate is the important part.** Seven refusals, each recorded as
`memory.rejected` with its reason: `no-source`, `malformed`, `user-refused`,
`hypothetical`, `protected-attribute`, `third-party`, `transient`,
`low-confidence`. A refusal that is not recorded cannot be audited for
over-rejection and leaves "why don't you know that?" unanswerable.

**Reconciliation has four outcomes and only one is an update**: confirm
(same value — observation count up, confidence up, asymptotic, hard ceiling
0.97), supersede (the world moved), dispute (equal support — raise it once,
never guess), write (new).

**The read path (§22.6).** Six components and one penalty, every score
logged: semantic (hash embedder), lexical (FTS5 bm25, rank-normalised),
recency (half-life by stability), importance (confidence × log observations
× pin), entity, **contradiction**, minus sensitivity. Then MMR for diversity.
Hard rules — pinned always in, secret out unless policy says otherwise,
retired and quarantined unreachable at any weighting — are enforced in SQL,
not in the scorer, because a filter inside a ranking function is one refactor
away from being a tie-break.

The contradiction bonus is positive and it looks like a bug. It is the single
most valuable thing in the scorer: without it, long-term memory becomes a
confirmation-bias engine that agrees with whatever was said most recently.

**Consolidation (§22.7).** Decay by half-life, rule review, distillation
(three or more episodes — never generalise from an anecdote), affect update,
identity card ≤400 tokens, user-readable digest. Idempotent, and tested for
it: decay is computed from the clock rather than multiplied down per pass,
episodes are marked as they are read, the card is content-keyed.

**The tools (§22.8).** `memory.recall`, `.list`, `.explain`, `.pin`,
`.correct`, `.forget`, `.export`. Reading is `safe`; forgetting is
`dangerous` with a `dryRun()` that shows the exact memories about to stop
existing — crypto-shredding cannot be undone, so the person approving has to
see what they are destroying. **There is deliberately no "write a memory"
tool**: a model that can write directly to long-term memory is a model that
can be talked into writing to long-term memory.

**Wired into the product.** `MemoryService` is constructed in `main.ts`, the
`MemorySource` seam M5 left empty is filled, the memory tools are registered,
and the HTTP layer primes recall before each run. The hash embedder ships
rather than being test-only: with no API key the agent still gets
hashed-semantic recall instead of an empty memories block.

## Bugs this milestone found in already-shipped code

Worth listing separately, because all four were green-tested before today.

1. **`facts` had no `principal` column** (since M1). Every query taking a
   principal was ignoring it. Invisible with one user; a cross-tenant leak
   with two. Found because the adversarial test for exactly this passed
   against two separate databases and therefore proved nothing. Migration
   008 adds the column, backfills it from the writing event, and the test is
   now one database and two people.
2. **`upsertRule` dropped everything but confidence on an existing rule** —
   which made rule retirement impossible, i.e. the mechanism §22.3 exists for
   could never fire.
3. **Rules were never learned from an utterance containing no facts.** An
   early return meant "please keep it short" — the clearest kind of
   preference anyone ever states — was discarded.
4. **`recallable()` did not exclude valid-time-closed facts**, so a
   superseded belief stayed recallable alongside the one that replaced it.

The golden file caught two more before they shipped: pinned memories appeared
twice in the prompt (once in the pinned block, once in memories), and
predicates rendered as "you prefers morning meetings". Both are now fixed,
and the identity card reads like something written about a person.

## Deferred, with reasons

- **No vector database.** §22 forbids it. FTS5 + an `Embedder` port. A real
  embedder is an adapter, not a rewrite.
- **No scheduler.** Consolidation runs after every 12 unconsolidated
  episodes, not nightly. The nightly trigger is M8's queue.
- **No Brier scoring or ask budget** — M7, and reaching for them here would
  blur the boundary.
- **No §22.8 UI in Veo.** The tools and the export exist and are tested;
  surfacing them as a memory inspector in the app is the obvious next piece
  of product work and it is not done.

## Unsure / known weak

- **Recall has two paths** (decision 029): the primed asynchronous one with
  embeddings, and a synchronous lexical fallback for runs that were not
  primed — scheduled runs recall worse than interactive ones.
- **The rule-override signal is noisy.** An override is inferred from an
  episode whose outcome was `corrected` while the rule was active. The
  correction may have been about something else entirely. It is conservative
  and it is wired, but it should be replaced by an explicit "that's not how I
  like it" signal rather than quietly trusted.
- **Distillation is crude**: repeated tool use becomes an `often_asks_for`
  fact. Honest, labelled `inferred`, and a long way short of §22.7's ambition.
- **The pattern extractor is ~17 regexes.** It is what makes the suite run
  offline and deterministic, and it will miss most of what a model would
  catch. `ModelExtractor` exists and is schema-validated — it drops any
  candidate whose quote is not found verbatim in the source text — but
  nothing exercises it offline.
- **Episode outcomes are self-assessed** at the end of the run. `corrected`
  can only really be known from the *next* turn, and nothing sets it yet.
- **`store.write()` stores `subject` as canonical JSON**, so M1's projector
  puts the whole JSON blob into the FTS text. Label text still matches; the
  rows are noisier than they should be. Not touching the M1 projector for
  cosmetics.
- **Affect is computed but barely used.** Four dials feed nothing yet.

## Addendum — §22.8 shipped in the product

The note above listed "no §22.8 UI in Veo" as a deferral. It is no longer
deferred: the user-control surface is built, on the wire and in the app.

**Routes** (`GET /memory`, `GET /memory/:id`, `GET /memory/digest`,
`GET /memory/export`, `POST /memory/:id/pin`, `POST /memory/:id/correct`,
`DELETE /memory/:id`, `DELETE /memory?subject=`). Search and filter by
basis, confidence, status and pin. `DELETE /memory` without a `subject`
is a 400 — "forget everything" must name its target rather than being
something a mistyped URL can do.

**Explain is generated from the record, not by the model.** An explanation
written by the same thing that might be wrong is a story, not an audit, so
the prose is assembled from the stored provenance: the date, the verbatim
quote, the observation count, the confidence, and any dispute or quarantine.

**The panel** lives in Settings → *What the agent knows about you*: the
identity card it would open a new conversation with, what it learned
recently, four tabs (Known / Pinned / Quarantined / Everything), search, and
per-row Why / Pin / Correct / Forget. Quarantined memories are **shown** —
they never reach a conversation, but "here is what a web page tried to make
me believe about you" is exactly what someone wants to see.

Screenshot: `docs/memory-panel.png`. Tests: 13 integration (`memory-api`),
6 e2e × 2 viewports.

### Three more bugs this found

1. **The service worker was caching `/agent/*`.** Stale-while-revalidate on
   every same-origin GET meant pinning a memory and re-reading the list
   returned the pre-pin copy — and, far worse, it wrote a plaintext copy of
   someone's memory into CacheStorage, where it would have outlived the
   crypto-shred that was supposed to destroy it. An agent that promises
   shredding cannot quietly keep a second copy in the browser.
2. **`GET /memory/:id` 404'd for a corrected belief.** `get()` hides
   transaction-time-closed facts from the *agent*, correctly — but the
   inspector has to show them, or a correction cannot be verified. Added
   `getAny()`.
3. **A shredded row rendered its own marker JSON** (`your name is
   {"$shredded":true,...}`) and kept its pin. It now reads "(forgotten —
   the content was destroyed)" and forgetting clears the pin, because a pin
   is an instruction to keep something in every conversation and there is
   nothing left to keep.

Also: API responses now send `cache-control: no-store`, and the client
fetches with `cache: 'no-store'`.
