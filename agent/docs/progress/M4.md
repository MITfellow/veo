### The capability set

```
granted = principal grants ∩ agent delegation ∩ ceiling(effective trust)
allowed = tool.capabilities ⊆ granted
```

Delegation is the layer that looks redundant and is not: "the user can send
email" does not imply "the agent may send email at 3am because a web page
suggested it". Nothing can widen anything else — a grant cannot raise the
trust ceiling, an approval cannot conjure a capability the principal lacks.

### Approvals

`dangerous` tool → `dryRun` preview → `approval.requested` → `run.suspended`
→ **the run function returns**. No timer, no promise, no continuation. The
resumable state is rows, which is the only reason the restart test works.

Resume re-enters at the step that asked, keeping `runId` and `stepId`, so the
outbox key is unchanged and an effect already committed is recognised rather
than repeated. Scopes: `once` / `session` / `shape` / `always`. The shape
matcher refuses inputs carrying a key it has never seen, so an approval
granted today cannot cover a `bcc` field added next year.

## Found while building

**The trust closure was wrong, and it was exploitable.** Effective trust was
computed over events carrying the *current* `stepId` — a closure of one step.
A FOREIGN tool result in step 2 left step 3 at USER trust, so a web page
could ask for a payment and get one. `web.post` genuinely executed in the
first corpus run. Three of the four layers were correct; the argument passed
to them was not. Only the end-to-end attack found it — which is the argument
for the corpus being a milestone bar rather than a unit test. Decision 023.

**Our own refusals were being fenced as untrusted.** A denial was tagged with
the step's effective trust, so the assembler wrapped the kernel's explanation
in `<<<UNTRUSTED_CONTENT>>>` and told the model never to follow instructions
inside it. The model was shown why it was refused and simultaneously told to
ignore that. Refusals are kernel-authored and now carry SYSTEM trust; this
cannot launder trust upward because the floor is recomputed from the log.

**The SSE stream had no redactor** — carried from M2 and closed here. The log
redacts on append and the invoker redacts observations, but a live token
delta goes model → stream → browser touching neither. A model mid-sentence
quoting a credential would have streamed it straight out. §31 says fuzz
*every* surface; this was the one nobody had pointed at.

**Egress had no durable record at all.** Per-run bytes lived in a counter
that died with the process, so §19's daily budget was unimplementable and
§14's "what did my agent talk to?" was unanswerable. One new event type,
deliberately (§9 permits it): decision 021.

**§12.3 and §33 pull in opposite directions.** The spec says a FOREIGN step
wanting more capability should escalate to a human; the bar says the corpus
must be *refused*. An approval dialog is only a refusal if the human reliably
says no, and the attacker gets unlimited attempts to generate plausible ones.
Resolved: escalation from TOOL and above, flat refusal at FOREIGN. Decision
022 — a deliberate narrowing of the spec, with the cost written down.

## Deferred

- **`always` does not yet write a procedural memory.** §19 says permissions
  and personalization are the same loop; the memory format arrives in M6, so
  the grant lives in the approvals table with a pointer to this note.
- **Expiry is not swept on a timer.** `expireStale()` runs on read and on
  boot. A scheduler is M8's business.
- **Per-principal budgets.** `DEFAULT_RUN_BUDGET` is one constant for one
  user; the shape is ready for a per-principal lookup, nothing reads one yet.
- **`policy.escalated` has no UI distinct from an ordinary approval.** The
  user sees "this needs you because …" rather than a dedicated escalation
  view. Enough to be honest, less than §12.3's "show them what content is
  asking for it" deserves — the asking content is summarised, not quoted.

## Unsure

- **Whether TOOL-trust escalation is the right line** (decision 022). It is
  defensible and it is a judgement call. The per-host promotion idea in that
  note is probably the real answer.
- **The daily ledger scans the day's events on every step.** Correct and
  rebuildable; at 100k events/day it will need the cache described in
  `budgets.ts`.
- **`trustForStep` reads the run plus the session's messages every step.**
  Same O(n) worry, same answer: correctness now, M5's incremental assembler
  later. It fails toward refusing, which is the right direction.
- **Shape matching only pins top-level scalars.** Deliberately narrow. I
  expect the first real complaint to be about nested objects, and I would
  rather add that with a test than guess at a matcher now.

## Decisions

021 egress is an event · 022 FOREIGN steps never escalate ·
023 a step's causal closure is the run.
