# 002 — The engine floor is Node 20, not Node 22

**Status:** accepted
**Date:** 2026-10-03

## Context

Appendix D.1 specifies `"engines": { "node": ">=22" }` and a `dev` script
built on `node --experimental-strip-types`, which first shipped in Node 22.6.

The only interpreter available in this environment is **v20.20.2**. There is
no nvm, no second install, and no package manager route to a newer one.

## Decision

`engines` declares `>=20`. The `dev` script compiles with `tsc` and runs the
JavaScript output instead of stripping types at load time.

## Consequences

* Nothing else changes. Every runtime feature the platform actually uses —
  `node:test`-free vitest, `node:util` `parseArgs`, `webcrypto`, `node:http`,
  WAL-mode SQLite, `ES2023` library targets — is present in Node 20.
* Type stripping was a developer-loop convenience, not an architectural
  commitment. Losing it costs a compile step in `npm run dev` and nothing in
  production, where the spec already runs compiled output from `dist/`.
* If a Node 22 interpreter becomes available this decision should be revisited
  and the floor raised, because `>=22` is the better default for a project
  that depends on `better-sqlite3` native builds.
* **This decision expires** if any later milestone needs a Node 22-only API.
  At that point the correct move is to raise the floor and state that the
  platform no longer runs here, not to shim the API.
