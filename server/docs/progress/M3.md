# M3 — Tools and effects

**Status:** complete. 43 test files, 535 tests, 16.8 s. `tsc --noEmit` clean,
`eslint .` clean at `complexity:10 / max-lines:400 / max-lines-per-function:50`,
zero `eslint-disable` in the project. Demo: `docs/progress/M3-demo.sh`.

## What M3 claims

The agent can now **do things**, and there is exactly one way for it to do
them. Everything the platform knows about whether an action may happen is
applied in `Executor.run()`, in one order, for every tool, with no second
path — asserted structurally, by reading the source tree, in
`test/unit/one-path.test.ts`.

## Built

**The tool contract (§26).** Everything the policy needs is *declared* —
`sensitivity`, `effect`, `tier`, `capabilities`, `idempotent`, `irreversible`,
`compensate`, `preview` — never inferred at call time. Nothing inspects a
payload or guesses from a name. The contract is checked at **registration**,
so a tool that cannot be used safely fails the process that loads it rather
than the user's first attempt to use it. The rules live in a `RULES` table;
adding a rule is adding a line.

**Six built-ins**, all real and offline: `time.now`, `memory.recall`,
`memory.assert`, `note.write`, `file.read`, `http.fetch`. The last has a real
contract and no transport (§2) — it refuses with `no_transport`. Omitting it
would have meant the external-effect path was never exercised by anything.

**The executor and its six gates**, in the order fixed by decision 012: plan →
budget → Rule of Two → capabilities and trust floor → autonomy → the call.

**The autonomy ladder (§30).** L0 propose-only, L1 observe, L2 interact, L3
effect, L4 irreversible. Untrusted content anywhere in scope caps the run at
L1 — and the result says so, rather than quietly behaving like an L1 run that
was configured that way.

**Approvals.** One-shot, expiring, bound by `stepSeal` to one step of one
plan. Only `USER` or `SYSTEM` may settle one. A declined step ends the run as
**cancelled**, not failed: the user answered the question, they did not break
anything.

**Budgets.** Steps, wall clock, tool calls and approvals, all counted against
the injected clock, with no setter — a run that can widen its own budget has
no budget.

**The audit trail.** `audit.ts` owns every event a run writes. Every
invocation is terminated on every path, a denial still writes `tool.invoked` +
`tool.denied` so a refusal is visible rather than absent, and a dry run writes
`tool.dryrun` and never `tool.invoked`.

**`arish tools`, `arish run <plan.json>`, `arish approvals [grant|deny]`.**

## What this milestone found

**The M0 gate caught the new projection, exactly as designed.** `approvals`
was in `PROJECTION_TABLES` and the 10k workload produced none, so
rebuild-identity failed on "approvals should have rows" rather than passing by
comparing emptiness to emptiness. Fixed in the *workload* — all four
settlement states, including denials, because a rebuild that lost a denial
would silently re-open a question the user had already answered.

**A frozen clock made the wall-clock budget untestable**, and the first
version of the test passed because the feature never ran. The harness now
takes `tickMs`, so time passes during a run and still passes identically on
every run.

**`budget.exceeded` acquired a payload schema**, which an M0 test asserted it
did not have. Repointed, not weakened — that is decision 003's mechanism
working, the same way `vault.unlocked` was repointed at M1.

**Four lint ceilings were design signals again.** `checkContract`'s 14-branch
staircase became a table; `executor.ts` at 461 lines became `audit.ts` (events)
+ `policy.ts` (gates) + `types.ts` (vocabulary) + a 236-line executor;
`parsePlan`'s hand-rolled validation became a zod schema that reports errors by
field name; `cli.ts` at 444 lines gave up `serve` and swapped its subsystem
if-chain for a table.

**The in-tool `dryRun` branches were unreachable** — the executor answers a dry
run from `preview()` and never calls `run()`. They now refuse with
`dry_run_misrouted` instead of returning a cheerful fake success, which turns
dead code into an alarm for the day something invokes a tool around the
executor.

## Deferred, with reasons

- **Retry and compensation.** `compensate` is declared and nothing calls it. An
  automatic undo that has never run is more dangerous than no undo, because it
  is believed.
- **Parallel steps.** Concurrency × approvals × budgets is a third thing to get
  wrong, and nothing here needs it.
- **Tools over HTTP.** `arish run` is the only door, so the authorisation
  question for a web caller has not had to be answered. M7.
- **Folding browsing into the executor.** Decision 010 already says browsing
  *is* a run; doing it would also resolve the two-audit-writer and
  tier-table divergences recorded in decision 012.
- **`turn.generate` driving the planner.** The plan comes from a file because
  there is no model (§2). When one is attached it produces exactly this JSON
  and nothing below it changes.

## Unsure

- `DEFAULT_BUDGET = { steps: 20, wallClock: 120s, toolCalls: 40, approvals: 5 }`
  and `DEFAULT_TTL_MS = 15 min` are guesses. The approval budget is the one to
  watch: five may already be more interruptions than a person tolerates before
  the interruptions are themselves the failure.
- The `MIN_AUTONOMY` tier floors, and whether irreversibility rather than tier
  is the right carrier of the jump to L4.
- `MAX_DETAIL = 200` / `MAX_REASON = 400`. Long enough to be useful, short
  enough that a hostile tool output cannot fill the log — neither bound is
  measured.
- Whether the browser's `{1, 2, 4}` tier table or M3's `{1, 2, 3}` is right.
  Both are defensible; having both is not.
